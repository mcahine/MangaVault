## 1. 现场结论（先说我查到了什么）

### 1.1 漫画库「下滑没法展开」——当前代码是通的，你那边跑的是旧前端

用无头 Edge + CDP **派发真实滚轮事件**（不是直接改 scrollTop）打在 8775 的实例上：

```
[滚轮前]   scrollTop=0      scrollHeight=6890   脚注「266 部匹配（本页 120 部，滚到底自动加载下一页）」
[滚轮后]   scrollTop=2400   scrollHeight=6890
[滚到底]   scrollTop=12266  scrollHeight=14665  脚注「266 部匹配（已加载 266）」
```

**滚轮能滚、触底能翻页、266 部全部加载完、控制台零报错。** 程序化 `scrollTop` 与真实滚轮两条路径都验证过。

所以问题不在代码，而在**你浏览器里跑的是旧 JS**。这和上一轮「桌面组件明明删了你还看得见」是同一个成因：你在修复落地**之前**打开过页面，浏览器把旧脚本按启发式规则缓存住了；服务端后来加的 `Cache-Control: no-store` 只能管住**新响应**，管不住已经躺在缓存里的旧条目。必须**硬刷新一次**（Ctrl+Shift+R / Ctrl+F5）才会换过来。

**但这暴露了两个真问题，必须修**（不能每次靠用户手动硬刷新）：
1. **无法自证版本**：界面上没有任何地方能看出「你现在跑的是哪一次构建」。所以只能靠猜。→ 加版本自检。
2. **翻页只有「触底自动加载」一条通道**：触底判定一旦在某个环境（不同缩放、不同浏览器、容器高度计算差异）失效，用户就彻底没辙，且没有任何提示。→ 加显式「加载更多」兜底通道。
3. **自动化测试有盲区**：`ui-scroll-check.mjs:170-181` 是直接设 `c.scrollTop = c.scrollHeight` 触发翻页的，**没有覆盖真实滚轮**，也没断言「总数从 120 涨到 266」。→ 补真滚轮 + 数量断言。

### 1.2 查重删除：其实删成功了，是界面没跟着更新

删除日志 `%LOCALAPPDATA%\MangaVault\dedupe\delete-log.jsonl` 里两次尝试，间隔 26 秒：

```
2026-10-15T05:17:14.360Z mode=recycle ids=2 ok=2 failed=0
    OK  「世界の終わりックス」をしよう
    OK  ～シスタークレアと淫らな秘密と噂の催眠アプリ～ フルカラー 総集編
2026-10-15T05:17:40.210Z mode=recycle ids=2 ok=0 failed=2
    FAIL 「世界の終わりックス」をしよう            | 路径不存在
    FAIL ～シスタークレアと淫らな秘密と噂の催眠アプリ～ フルカラー 総集編 | 路径不存在
```

磁盘复核：两个目录**都已不在原位置**（确实进了回收站）。第一次就成功了；第二次失败是因为东西已经没了。

**所以「执行删除没成功」的真实体验是**：删成功了 → 但 `scan-latest.json` 没被更新（`src/modules/dedupe/index.mjs:328-351` 的删除路由只写删除日志，**不回写扫描结果**）→ 前端 `load()` 重新拉到的还是那两条单元 → 你以为没删掉 → 再点一次 → 得到「路径不存在」→ 判定为「删除失败」。

**修复方向**：删除成功后，把已删单元从扫描结果里移除（或标记 `deleted` 并从列表过滤），并在界面上明确显示「已删除 N 个，去回收站可还原」。

### 1.3 查重缩略图大量 400（顺带发现的真缺陷）

服务日志里成片出现：

```
WARN [server] GET /api/dedupe/thumb?unit=...&side=lib&name=JK淫乱的日常/4 5/001.jpg -> 非法文件名
WARN [server] GET /api/dedupe/thumb?unit=...&side=lib&name=.../001.png -> 非法文件名
```

根因：库侧图片名是**带子目录的相对路径**（`漫画/章节/001.jpg`），而 `engine/paths.mjs:164` 的 `isPlainFileName()` 明确禁止 `/\`；只有带了 `root=` 参数才会走 `isSafeRelPath()` 那条放行分支（`index.mjs:289-294`）。而前端 `public/modules/dedupe.js:167` 构造 lib 侧缩略图时**没带 root**：

```js
const libUrl = u.libDir && libSample ? thumbUrl(u.id, 'lib', libSample.lib) : '';   // ← 缺 root
```

后端 `pairs` 里其实**已经算好了 root**（`index.mjs:259`），前端却丢掉了。→ 库侧缩略图全灭，对比视图右半边基本看不到图。

### 1.4 桌面端跑查重会把 exe 关掉——看护太严 + 事件循环被饿死

宿主 `desktop/host/Program.cs` 的看护逻辑：

| 位置 | 内容 |
| --- | --- |
| `Program.cs:58` | `PING_INTERVAL_MS = 3000` |
| `Program.cs:59` | `PING_MAX_FAILS = 4` |
| `Program.cs:171` | 定时器每 `1000ms` 跑一次 `WatchdogTick` |
| `Program.cs:683-684` | `TryGet('/api/ping', 2000)`，成功就清零失败计数 |
| `Program.cs:690-696` | **连续 4 次失败 → `Dump("SERVERDEAD")` → 直接收摊** |
| `Program.cs:677-681` | node 进程退出 → `SERVER-DEAD-EXIT` → 收摊 |

而查重的像素比对是**同一个 Node 进程里的同步重活**：`engine/match.mjs` 的粗筛要对**全库 63395 张**的 64 字节指纹做线性扫描（`searchRange`，`match.mjs:63-77`，早停阈值 `SEARCH_LIMIT = 64*14 = 896`），每个单元都要跑一遍；`runPixelStage` 只在收尾处 `await sleep(0)`（`match.mjs:286`），单元内部的循环**不让出事件循环**。

结果：单次同步工作一旦超过 ~2 秒，`/api/ping` 就会超时；连着 4 次（约 4–8 秒）宿主就判定「后端死了」→ 关窗。**这和上一轮我实测到的「扫描中途 ECONNRESET」是同一个现象。**

**修复方向**：①把查重扫描搬进 `worker_threads`（HTTP 事件循环不再被饿死）；②热循环里显式让出（`await setImmediate`）；③宿主看护区分「进程已死」和「进程活着但正忙」——扫描期间放宽阈值（或让后端暴露进度心跳供宿主判断），绝不能因为忙就关用户的窗。

### 1.5 查重算法现状（优化前的基线，全部实测）

| 项 | 现状 | 出处 |
| --- | --- | --- |
| 指纹规格 | 32×32 灰度（1024 字节/张），另存 8×8 子集当粗筛键（64 字节） | `python/build-fp.py:54`、`match.mjs:46` |
| 粗筛 | 对全库线性扫描，早停阈值 `SEARCH_LIMIT = 64*14 = 896` | `match.mjs:9,63-77` |
| 抽样投票 | `SAMPLES = 8` | `match.mjs:10` |
| 判重阈值 | 灰度平均绝对差 `pixelThreshold` 默认 **8** | `match.mjs:89,205` |
| 增量 | 按文件 `mtime` 决定是否重算指纹 | `build-fp.py:25,39` |
| 并行 | Python `ProcessPoolExecutor`，`max_tasks_per_child=20` | `build-fp.py:108` |
| **实测耗时** | 库侧指纹 **约 19 分钟**（63397 张）/ 查重侧 **约 6 分钟**（12660 张）/ **像素比对本身只要 75–84 秒** | 本会话实测 |
| **实测精度问题** | 查重侧是 **webp**、库侧是 **jpg**，字节阶段必然全灭（140 单元里 139「未找到」）；同作品图片序列**精确错位一张**（库侧多一张封面），导致部分匹配被算歪 | 本会话实测 |

**结论：慢的不是比对，是指纹构建；不准的不是阈值，是「没有归一化 + 没有序列对齐 + 封面没排除」。**

## 2. 改造方案

### 2.1 漫画库滚动（前端可诊断 + 双通道 + 测试补盲）

| 项 | 方案 |
| --- | --- |
| 版本自检 | `/api/version` 返回 `{ build, startedAt, files: { 'public/app.js': sha256前8位, ... } }`；页面左下角「关于」与设置页显示「前端资源指纹」，**一眼能看出跑的是哪份代码** |
| 双通道翻页 | 保留触底自动加载；网格底部**常驻**「加载更多（已显示 120 / 266）」按钮，触底失效时仍可手动点；加载中/到底/失败三态都有明确文案 |
| 强制换新 | 模块 import 已带 `?v=Date.now()`，保留；`index.html` 与 `app.js` 补 `no-store`（已做）并加 `<meta http-equiv="cache-control" content="no-store">` 兜底 |
| 测试补盲 | `ui-scroll-check.mjs` 改为 **CDP `Input.dispatchMouseEvent` 真实滚轮**；新增断言：脚注从「本页 120 部」变为「已加载 266」、`scrollHeight` 单调增长、「加载更多」按钮在触底失效时可用 |

**验收**：真滚轮滚到底 → 断言总数 120→240→266；「加载更多」按钮点击也能加载；`/api/version` 能在页面上看到。

### 2.2 查重算法（更准 / 更快 / 可解释）

**更准（三件事，按收益排序）**

1. **亮度/对比度归一化后再比**：现在的 MAD 直接吃原始灰度，重编码（webp↔jpg）带来的 gamma/亮度漂移会顶到阈值 8 的边缘。改为对每张图先做**均值-方差归一化**（或直方图均衡）再算差异 —— 这是「同图不同编码」误判「部分重复」的主因。
2. **排除封面 + 序列对齐**：实测同一作品「库侧比查重侧多一张封面、序列整体错位 1」。方案：识别各目录的封面文件（`cover.jpg`/首图，以及 `library/scanner.mjs` 同款规则），对齐时把它排除；然后用**序列对齐**（LCS/DTW 在逐页相似度的矩阵上求最优路径）替代现在的「投票 + 计数」，把「部分重复」的覆盖率算对。
3. **两级复核 + 置信度**：粗筛 8×8 → 中检 32×32 → 对候选做 **64×64 复核**；输出不再是单一个 MAD，而是 `{覆盖率, 最优路径, 平均差, 最大差, 差异热区}`，界面上把差异位置标出来，让人**看得懂为什么判重**。

**更快（四件事，按收益排序）**

1. **指纹构建提速（19 分钟的大头）**：Pillow 解码后用 `im.draft('L', (64,64))` **在解码阶段就降采样**（JPEG 专用，通常快 2–5 倍），再 `thumbnail()` 到 32×32；避免现在「全尺寸解码 → LANCZOS 缩到 32×32」的浪费。
2. **指纹缓存键从 mtime 换成「内容特征 + 规格版本」**：现在是 `mtime`（`build-fp.py:39`），改编码、换文件名、同秒覆盖都会失效重算；改成 `size + mtime + 指纹规格版本号`，并给规格升版留迁移位。
3. **索引替代线性全扫**：粗筛键是 64 字节，全库 63395 条 = 4MB。改成对 **4×4=16 维**做 LSH 分桶 / VP-tree，先把候选压到几百条再精算，比对阶段（现 75–84 秒）可再降一个量级。
4. **worker_threads 并行比对**：比对现在是单线程；按 CPU 核数切分单元并行（**同时解决 §1.4 的事件循环饿死**）。
5. **跳过已决策单元**：已经打了 `keep`/`delete` 的单元在增量重扫时不再重算。

**验收基线（必须复现的数字）**

| 指标 | 现状 | 目标 |
| --- | --- | --- |
| 库侧指纹构建 | 约 19 分钟 / 63397 张 | **≤ 6 分钟** |
| 查重侧指纹构建 | 约 6 分钟 / 12660 张 | **≤ 2 分钟** |
| 像素比对 | 75–84 秒 / 140 单元 | **≤ 30 秒** |
| 已知 5 组肉眼重复对 | 需人工比对 | **100% 命中**（§1.1 已列出的 5 组） |
| 公开接口误判 | 无基线 | 抽样 200 张**跨作品**图片，误报率 **0** |

### 2.3 删除链路（删得掉、看得见、能还原）

| 项 | 方案 |
| --- | --- |
| 删除后状态一致 | 删除成功后把单元从 `scan-latest.json` 移除或标 `deleted`，`/api/dedupe/units` 默认过滤；列表随即消失 |
| 结果可见 | 返回值区分「成功 / 已不存在 / 权限失败」三种，UI 分别提示；成功时给「已移入回收站」与「去还原」两个动作 |
| 幂等 | 对「路径不存在」不再当成失败报错，而是提示「该单元此前已删除」，并把这条计入 `skipped` 而不是 `failed` |
| 缩略图修复 | 前端 lib 侧缩略图**带上 `root`**（`pairs[].root` 已有）；后端在能唯一确定所属库根时也接受安全子路径，双保险 |
| 测试 | 新增接口级用例：删除成功 → 列表不再出现；重复删除 → `skipped` 且不报错；`side=lib` 带子目录名 → 200 而不是 400 |

### 2.4 桌面端不再被查重搞崩

| 项 | 方案 |
| --- | --- |
| 不饿死事件循环 | 扫描搬进 `worker_threads`；热循环里 `await setImmediate` 让出（先做，收益立刻可见） |
| 看护说人话 | 宿主区分「进程已退出」（立即收摊，保持现状）与「进程活着但 ping 超时」（放宽到 20 次 ≈ 20 秒，并在 trace 里记 `SERVER-BUSY`）；**绝不能因为忙就关用户的窗** |

## 3. 明确不做 / 已排除

- **不改判重阈值来「凑」结果**：精度问题按 §2.2 的归一化 + 对齐解决，调阈值只是把误报换成漏报。
- **不把回收站改成永久删除**：默认仍是 `recycle`，可还原是底线。
- **不为省事删掉 32×32 灰度链路**：它是快速通道，改为「快筛 + 复核」两级。
- **不动字节级 SHA-256 阶段**：它对「同编码重复」仍然最准，只是对本例的 webp↔jpg 天然无效，保留。
